29. [ARCH] [FID|CRITIQUE] Orphan/widow control ("never one word alone on a line") cannot be solved by CSS `text-wrap: balance`/`pretty` alone, even when applied correctly to every shared heading/body class: (a) a class-name-substring inventory (kicker/label/title/quote/heading) reliably MISSES real offenders: on one 9-page site, 3 of 5 confirmed orphans were on classes absent from the initial inventory (`hero_rating-caption`, `cta_founder-quote`), only surfaced by a DOM sweep of actual rendered `h1-h4,p` tags at each breakpoint; (b) `pretty`'s browser heuristic still leaves real single-word last lines on some long sentences at some viewport widths even once applied, confirmed live on a card body and a founder quote. Reliable process: apply `text-wrap:balance` on heading-tier classes of 3 lines or fewer and `text-wrap:pretty` elsewhere (L-110) at the shared class level for global coverage, THEN run a DOM-based sweep on the PUBLISHED page: for every text element, walk its text nodes with `document.createRange()` per word, read each word's `getBoundingClientRect().top`, group into lines with a tolerance band (~6px; different inline font-sizes, e.g. a mailto link styled smaller than its surrounding paragraph, otherwise produce false-positive "line breaks" from `Math.round(top)` alone), and flag any element whose last line-group has exactly one word. **Compounding factor.** The script did have a `setTimeout` safety net, but it lived INSIDE the per-counter animation function, which only executes after the observer callback fires. A safety net downstream of the thing that failed protects nothing. This is L-48 in a different costume: the guard tested a proxy rather than the outcome.

**Guardrail.** Any IO-driven reveal needs two additions beyond the observer: (1) at init, synchronously check `getBoundingClientRect().top < window.innerHeight` and trigger immediately if the element is already at or above the fold, which covers both already-in-view and already-passed; (2) an independent global fallback timer that force-reveals and writes final values if the trigger has still not run. **Measurement trap.** In a backgrounded tab (`visibilityState: hidden`) CSS transitions do not advance, so a correctly-revealed element reports `opacity: 0` indefinitely. The agent browser pane is permanently hidden, so opacity alone cannot verify a reveal there and will manufacture a false regression. Distinguish the two: check whether the trigger CLASS was applied. **Detection.** Test the load-past case explicitly: set scroll below the section, hard reload so restoration kicks in, then count elements at `opacity: 0`. A pass on a top-of-page load proves nothing about this failure. Scrolling the page synchronously in one JS task also will not fire the observer, so distinguish that measurement artefact from the real defect by checking whether the trigger class was ever applied, not just current opacity.

### L-72 — A gradient can be made hover-animatable with a pixel-identical resting render by authoring it at `background-size: N%` with every stop divided by N/100   [FID|BUILD]

- Root cause: the MCP is configured with `--browserUrl=http://127.0.0.1:9222` and never launches Chrome itself, and its file writes are confined to the Claude Code workspace roots. Neither fact was in the agent's setup steps; the runbook named a fallback without a command.
- Guardrail: before the first chrome-devtools call, run `bash ~/.claude/lib/debug_chrome.sh` (add `--headed` for WebGL liveness checks) and continue only on its `ready` line. Every `filePath` or `outputDirPath` passed to chrome-devtools goes under `~/.claude/_scratch/YYYY-MM-<job_id>/`, never the session scratchpad or `/tmp`.
- Detection: `lib/agent_telemetry.py` counts `chrome_connect_errors` and `artefact_path_denied` per dispatch. A non-zero value on any run after 2026-09-27 means the setup step was skipped.

### L-108: Webflow MCP calls need session_id, one agent_id and exact action keys, and an attributes write replaces the whole list   [API|BUILD]
- Context: 2026-09-27 audit: 44 Webflow MCP calls in FLOWSMITH transcripts failed schema validation, and the live schemas now require `session_id`, `agent_id` and `context` on every call.
- What went wrong: calls used action names or shapes that do not exist (`get_page_settings`, `get_attributes` sent to `data_element_settings_tool`, `query_styles` with `style_names`, `text` placed on a `query_elements` query instead of inside its `element_filter`), omitted the top-level `siteId` and `pageId` that some tools require, put ids at the top level where the action wanted `site_id` or `page_id`, or batched code-carrying actions whose escaping broke the JSON.
- Root cause: call shapes were written from memory, and similar actions live on different tools. Attributes are `data_element_tool` `get_attributes`, `set_attributes` (adds or updates the named attributes, leaving the rest) and `remove_attribute`. `data_element_settings_tool` `set_settings` key `attributes` is a different path that replaces the whole list. Corrected 2026-09-27 after the first version of this entry pointed at the replace-all path.
- Guardrail: load each Webflow tool's schema with ToolSearch before its first call in a run and copy action keys from the schema. Send `session_id: "start"` on the first call and the issued `ses_` value on every call after it; send one `agent_id` for the whole run. Top-level ids are camelCase (`siteId`, `pageId`) and only where the schema lists them; ids inside an action are snake_case (`site_id`, `page_id`). Write static attributes with `data_element_tool` `set_attributes` and `remove_attribute`; use `set_settings` key `attributes` only for bound (CMS or prop) attributes, and only after reading the current list with `get_settings` and writing the full merged list, because it replaces the list and silently drops Finsweet and runtime attributes. Send any action carrying embedded code as its own call.
- Detection: `lib/agent_telemetry.py` counts `schema_errors` per dispatch. Any `InputValidationError` or `-32602` on a Webflow tool after 2026-09-27 means the schema was not loaded first.

### L-109: A staging publish is defined by publish_site parameters, not by which site you think you are on   [LIVE|BUILD]
- Context: 2026-09-27 emulated read-only smoke on the Project S "staging" site. `list_sites` showed four production custom domains attached to the same site (<client-domain>, <client-domain> and both www. forms), all sharing the webflow.io host's last-published time.
- What went wrong: nothing shipped, but the agent prompt called staging publishes routine while the live `data_sites_tool` schema publishes to whatever `customDomains` lists and to the webflow.io host only when `publishToWebflowSubdomain` is set. On a site with production domains attached, "publish to staging" was one parameter away from a production release that needs approval.
- Root cause: staging was treated as a property of the site rather than of the publish call, and no step listed a site's domains before publishing.
- Guardrail: call `get_site` once per run and record every attached custom domain. A staging publish passes `publishToWebflowSubdomain: true` and `customDomains: []` explicitly. Any `publish_site` call with a non-empty `customDomains` is a production publish: stop and raise the approval card first.
- Detection: after each publish, curl the webflow.io URL and each custom domain with `-I` and compare `last-modified`; a custom domain whose timestamp moved on a staging publish is a production release that skipped its gate.


### L-110: Balanced wrapping on list items and labels breaks short lines early, so `text-wrap: balance` stays on short headings   [FID|BUILD,CRITIQUE]
- Context: 2026-08-10 build and 2026-09-09 client review of a marketing site. Following dod.md §4b, the agent wrote `text-wrap: balance` through the style tool to the Designer class behind a packages tick list. The client logged seven BugHerd tasks (#13 to #19) against it.
- What went wrong: `balance` evens out line lengths, so list items that would have filled one and a half lines broke near half width and left narrow ragged blocks that the client read as a layout bug. It was patched per page, first with a `text-wrap: wrap` override and then with `pretty`, and never reached the ledger, while rule 29 put labels on `balance` too (amended by this entry).
- Root cause: until 2026-09-28, dod.md §4b assigned `balance` by class tier, including stat labels and quote and caption classes, with no length limit. `balance` suits headings of a few lines; on multi-line list items, labels and card bodies it trades a filled row for an even but narrow block.
- Guardrail: write `text-wrap: balance` only to heading-tier classes (H1 to H3, kickers, card titles) whose rendered text runs to 3 lines or fewer at every sweep width. List items, labels, captions, quotes and card bodies get `text-wrap: pretty`, and any orphan that survives gets the nbsp fix from rule 29. Before writing `balance` to a class, list every element carrying it on the published page and confirm each is a heading of 3 lines or fewer.
- Detection: at each sweep width on the published page, flag any element outside the heading tier (H1 to H3, kickers, card titles) whose computed `text-wrap-style` is `balance` and whose widest line (from `getBoundingClientRect` over `Range` rects) is under 75% of its content box width. A critique row citing the classes checked, and the widest-line ratio of each, passes; no row fails.

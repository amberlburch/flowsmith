L-106 (renumbered from L-86 on 2026-09-27; number collided) [DEFECT-CLASS] Two absolutely-positioned overlay elements pinned via top/bottom percentage to opposite ends of a shrinking container will collide at some intermediate breakpoint even when both endpoints (largest and smallest tested width) look clean -- because container height scales continuously with viewport while element height is content-driven and near-fixed, the geometry only needs `2 x elementHeight > containerHeight` to be true somewhere in between. -- because a client hero's two floating stat cards (top:8%/bottom:6% over a portrait image) were verified clean at 1440 (209px gap) and, after a fix, at 992/375/768 (stacked treatment), but a narrow 992-1060px band was still on the absolute-overlay CSS and the cards physically overlapped there (58px overlap at 992, crossing to clean only above ~1058px) -- confirmed the SAME containers were already at zero-margin at the old, shorter card height (2x128=256=containerHeight exactly), so this was a pre-existing fragile state a content-length change (2-line vs 1-line caption, +11px card height) tipped into a real, visible defect. This is the same root-cause family already named 3x earlier in this build and captured as checklist criterion B7 (decorative-connector alignment) -- but B7 only checks connectors, not overlay-vs-overlay collision, so this instance still had to be found by hand at the exact breakpoint. When two floating/absolute elements are pinned to opposite ends of a container whose size scales with viewport, test breakpoints BETWEEN the two verified-clean endpoints, not just at them, and if a collision is found, extend the proven-safe stacked/static treatment to a custom-width media query band (not a native breakpoint) covering the empirically-measured crossover with margin, per the same technique already used for the mobile-rail 768px fix. (2026-08-19)

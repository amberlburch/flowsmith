L-87 [DEFECT-CLASS] A hand-inlined SVG (wordmark, icon, logomark) can silently ship with missing `<path>` elements -- the viewBox is sized correctly for the full mark but only some of the paths actually got copied in, rendering a visibly truncated/incomplete glyph with no error anywhere in the pipeline (API success, valid SVG, no console warning) -- because a client footer wordmark's SVG had viewBox="0 0 83.042 18.8666" (clearly sized for the full 6-letter wordmark) but only 3 of the needed path elements existed, rendering the first 3 letters -- confirmed via getBBox() on the live element: path content bounding box stopped at x=43.58 out of the 83.042-wide viewBox, i.e. only ~52% of the declared width actually had geometry. This is the second confirmed instance of this exact failure shape in one build (first: a LinkedIn footer icon transcription error, D22, caught before publish only because a pathCount comparison against a known-good reference existed at the time). The wordmark instance was NOT caught at build time because it was the mark's first inlining -- there was no reference to diff pathCount against, and no other check exists that would catch "valid SVG, wrong number of paths for what it's supposed to depict." When inlining ANY multi-path SVG (wordmark, multi-stroke icon, logo) with no prior working instance on the site to diff against, verify path count against the SOURCE FILE (not just "did the API call succeed") before publishing, and if no source file is available, render the fresh insertion and visually confirm the rendered glyph actually reads as the intended word/icon -- do not treat "the SVG is syntactically valid and the viewBox looks right" as proof the content is complete, since Webflow's API validates SVG syntax, not semantic completeness. Real text should be preferred over a hand-inlined multi-letter wordmark wherever the design allows it (as the nav on this same build already does), since text has zero transcription-error surface and no font-fallback catastrophe mode. (2026-08-19)

L-88 [DEFECT-CLASS] An element attribute (e.g. `hidden`) or a page's freeform code, written via the Data API, can read back correctly through the API's own GET (get_attributes / get_page_freeform_code echoes the write) while never actually reaching the published output -- confirmed twice in one session on a client build. Instance 1: the article template's freeform code, read via get_page_freeform_code, contained a working-looking readmore-href-repair script; curl of the live published article page showed the script had no effect (hrefs stayed href="#"). Instance 2: an earlier `set_attributes` call to add `hidden=""` to the Resources empty-state element read back as present in a subsequent query_elements call; curl of the live page showed no `hidden` attribute at all. Both were on pages/elements that had NOT been explicitly re-published after the API write that supposedly landed it (the write may have gone through on a prior session's draft state, or a subsequent publish for other work may not have included this specific delta for reasons not established). This is a new, narrower instance of the general "API success != published truth" pattern the golden rule already covers, but specifically dangerous because it fools even a careful agent: querying the element or freeform block via the SAME API that wrote it returns the expected value, so a check that stops at "does the API confirm my write" (rather than curling the live URL) will report false-positive success. Guardrail: after ANY attribute or freeform-code write intended to change served behavior, verify via curl against the published URL with a cache-busting query param -- never trust get_attributes/get_page_freeform_code alone as proof the write is live, even though for most other write types in this project's history a same-session API echo has been a reliable signal. When a mismatch is found, the safe recovery is to overwrite with a known-good value and republish + re-curl, not to assume the stored value will eventually take effect. (2026-08-19)

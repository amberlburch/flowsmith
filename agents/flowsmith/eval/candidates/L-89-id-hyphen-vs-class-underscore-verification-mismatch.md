L-89 [PROC] A Webflow element commonly carries two different naming conventions for conceptually the same name -- an HTML id attribute in hyphen-case (e.g. id="resources-search-empty") and a Webflow-generated style class in underscore-case (e.g. class="resources-search_empty") -- and a freeform CSS fix targeting the ID selector can be genuinely live and correct while a verification pass that searches for the underscored class-name string inside inline <style> blocks finds nothing, producing a false "the fix isn't there" read even with correct cache-busting and correct methodology otherwise. Surfaced on a client site's Resources empty-state fix: the coordinator's re-check printed the compiled stylesheet's `.resources-search_empty{...}` rule (correctly showing no display property, since that's not where the fix lives) and reported no rule found in any inline `<style>` block -- but a fresh check by the author found `#resources-search-empty{display:none}` clearly present in the third inline block. Both parties were right about what they found; the mismatch was almost certainly a hyphen-vs-underscore string-match miss, not a live/dead discrepancy. Guardrail: when verifying a freeform CSS fix on any element, check the ACTUAL id and class attributes on the served tag first (they are frequently NOT the same string, just similar), and search inline style blocks for BOTH naming conventions before concluding a fix is absent. When reporting a "not found" result to a collaborator, paste the exact search string used alongside the negative result, so a hyphen/underscore (or any other naming-convention) mismatch is visible immediately rather than requiring a second full investigation round to surface.
